欢迎回来，这里是 [@LemonNekoGH](https://github.com/LemonNekoGH)，AIRI 的维护者之一。

上一篇 Dome Keeper 的 DevLog 还停在 [2026.02.16](../DevLog-2026.02.16/index.md)，那会儿我还在吭哧吭哧地采 YOLO 数据集。转眼大半年，这条线换了好几拨方向，最后落到了一个我自己觉得最好玩的题目上：**怎么让 AI 真的把手放到键盘上**。

## LLM 太慢了，所以得分层

一切从一个小小的、有点扫兴的观察开始：把「下一帧该按住哪个键」直接丢给 LLM 是不行的。

Dome Keeper 里，怪物贴脸的时候你得马上转身开火；矿石就在脚边的时候你得立刻按下去。这些决定的寿命是几十毫秒。而就算是最快的 LLM，一次推理往返也在几百毫秒到几秒之间——等它想好，灯塔已经被啃掉一半了。

所以 [ADR-0004](https://github.com/proj-airi/game-playing-ai-dome-keeper/blob/main/docs/decisions/0004-adopt-a-multi-timescale-gameplay-agent.md) 把这套东西拆成了三层：

- **AIRI** 管整局游戏该不该开始、该不该停，以及你的意图和记忆；
- **Upper Agent**（一个 LLM）负责中频决策，比如「先去挖点铁，攒够了回来升级钻头」；
- **Lower Agent** 负责高频控制，把上面那句模糊的意图翻译成「这一秒钟按住 `ui_right`」。

一句话：上层想战略，下层拼手速。两者跑在完全不同的时间尺度上，中间靠「任务」串起来。

那下一个问题就很自然了——这个手速飞快、又要看画面的 Lower Agent，到底该怎么做？

## 先从最小的动作单位开始

在训练任何东西之前，得先把「动作」这个词定义清楚。

我在 mod 里引入了一个叫 **Quark Action** 的概念。名字有点怪，但我很喜欢它。传统上大家会叫这种东西「原子动作（Atomic Action）」，可我觉得不对——原子又不是物理里最小的东西，凭什么它就得是终点呢？所以换成了夸克。

Quark Action 的定义只有一条：**它是无状态的、只针对当前这一帧和当前世界状态的一次输入求解**。它不记得上一帧做了什么，也不关心任务成没成功。比如负责移动的那个，长这样：

```ts
export class _MoveQuarkAction extends RefCounted {
  static resolve(current: Vector2i, target: Vector2i): string {
    if (current.x < target.x)
      return 'ui_right'
    if (current.x > target.x)
      return 'ui_left'
    if (current.y < target.y)
      return 'ui_down'
    if (current.y > target.y)
      return 'ui_up'

    return ''
  }
}
```

输入是「我在哪、要去哪」，输出是「这一帧按住哪个方向键，或者什么都不按」。干净得不像 AI 代码——因为这一层本来就**不该**有智能，智能在上面。

现在 mod 里一共有这些 Quark Action：`Move`、`Pickup`、`Drop`、`Activate`、`AimLaser`、`FireLaser`。它们各自只负责一件事，而且只在「条件真的满足」时才给出输入：`Pickup` 只在你已经聚焦到那个物体时返回 `keeper1_pickup`，`Activate` 只在精确对准了目标 `Usable` 时才返回 `ui_select`。

## 任务层：借 HTN 的皮

单个 Quark Action 解决不了「走过去把铁捡起来」这种问题，因为那需要持续好几个帧、还要根据中间结果决定下一步。于是上面套了一层 `TaskExecutor`。

它的结构借了分层任务网络（HTN）的词汇：

- **复合任务（compound）** 负责把一个大目标拆成有序的子任务；
- **基本任务（primitive）** 负责在每一帧求解一个 Quark Action；
- 只有最活跃的那个基本任务叶子节点，才有资格产生游戏输入。

举个例子：`PickupTargetTask` 会先朝着目标矿石走，走到聚焦了才按拾取键，直到它真的挂到 Keeper 身上才算完成；`DropByType` 更绕一点——因为游戏的「丢弃」按键没法指定丢哪一个（它总是丢掉离你最近的那块），所以这个复合任务会先不停地短按，一直按到掉出来的是想要的那种资源，再把之前误掉出来的其他资源一个个捡回来。

调度频率是 **10 Hz**——每隔 6 个物理帧检查一次。也就是说，Lower Agent 每秒做 10 次决定，这个数字后面很重要。

需要强调的是：`TaskExecutor` 只是借了 HTN 的皮，它不是完整的 HTN 规划器。没有反向规划、没有备选方法回溯、没有重规划。它只按一个写死的顺序跑下去。

## 低层动作分类器：Lower v0

有了这套结构，就可以采集数据、训练真正的「手」了。这就是 [ADR-0005](https://github.com/proj-airi/game-playing-ai-dome-keeper/blob/main/docs/decisions/0005-train-lower-v0-with-automated-multitask-demonstrations.md) 里的 **Lower v0**。

### 为什么是行为克隆，不是强化学习

最直接的问题是：为什么不做 RL？

答案很朴素——**手上没有那个算力**。我只有一台 Apple M5 Pro（64 GB 统一内存）和一张 RTX 3060（12 GB 显存）。VPT 那条「先训逆动力学模型再训策略」的路子确实漂亮，但它的规模对这套机器来说太重了，跑不起来。

更妙的一点是：**演示数据根本不用人来录**。因为 `TaskExecutor` 本来就会玩，让它自己跑一遍、把过程录下来就行。于是我们没有去当人肉标注员，而是写了一个 mod，用可控场景自动生成演示。

### 模型到底看什么

Lower v0 是一个「动作分类器」：在每一个决定点，它预测**下一刻该按住哪个动作**。输入是三个张量：

| 输入 | 形状 | 含义 |
| --- | --- | --- |
| RGB 帧 | `[10, 3, 216, 384]` | 最近 10 帧完整画面（最老的在前） |
| 历史动作 | `[10, 9]` | 每一帧拍摄时正按着的动作（one-hot） |
| 指令 | `[9]` | 4 个任务位 + 5 个目标位（one-hot） |

指令是结构化、封闭的，只有这么几种合法组合：

| 任务 | 合法目标 |
| --- | --- |
| `pickup` | `iron` / `cobalt` / `water` |
| `drop` | `iron` / `cobalt` / `water` |
| `activate` | `gadget_chamber` |
| `attack` | `monster` |

输出是 9 个分数，对应 9 个动作类：`ui_up`、`ui_down`、`ui_left`、`ui_right`、`ui_select`、`keeper1_pickup`、`keeper1_drop`、`dome1_fire`，以及 `none`。

这里有个容易搞混的地方：这 9 个类描述的是**期望的「按住状态」**，不是孤立的按键事件。重复同一个类等于维持当前按住的动作；同一时刻只有一个类是激活的。而 `none` 只是「松开这个控制器按住的键」，**它不代表任务完成**。

网络本身很朴素：一个共享的 ResNet-18（ImageNet 预训练，去掉最后的分类层），把每帧压成 512 个视觉特征，10 帧就是 5120 个；再拼上 90 个历史动作值和 9 个指令值，一共 5219 个输入；最后过一个 MLP，输出 9 个分数。CNN 和 MLP 是一起训练的。

### 因果对齐，别偷看未来

训练这种东西最容易翻车的地方，是让模型不小心「偷看未来」。

所以对齐规则写得很死：预测第 `t` 个动作时，输入只包含 `F_(t-9)` 到 `F_t` 这 10 帧，以及 `H_(t-9)` 到 `H_t` 这 10 个历史动作。**输入里永远不会出现 `A_t` 本身、更晚的帧、或者这一局的结局**。会话开始时，缺的帧用第一帧补齐，缺的动作用 `none` 补齐；窗口绝不跨会话边界。采集器存的是整段会话，训练加载器再去切出重叠的窗口。

听起来是本分，但真的很容易写错——尤其是任务切换、输入松开、取消这些事件，它们可能落在 10 Hz 网格的缝隙里，所以会话里老老实实记了它们的真实顺序和物理帧号，而不是硬凑一个对齐的时间戳。

## 数据是怎么攒出来的

采集也全自动：`mise run lower-v0:collect` 会为每种指令跑 8 个带种子的场景，用已有的 ViKeeper fixture 当底座，把矿物、怪物、装备室按种子摆在可控的位置上。

有一个小细节挺折磨人的：采集时游戏窗口**不能获得焦点**，不然会打断你自己在干别的事情。所以录制走的是 Movie Maker 流程，先录成视频，事后再用 ffmpeg 抽出 384×216 的 RGB PNG，并校验帧和动作的对齐。**只有成功完成、且帧/动作完全对齐的会话才会被提升进数据集**；失败、超时、中断的会留在 `.incomplete` 里，永远进不了训练集。

最后冻结下来的是 `frozen-20260911` 这个快照：**166 个会话、2727 帧**（其中 160 个是早期会话，6 个是新的多货混装 Drop 场景）。

## 它现在跑成什么样了

训练配置平平无奇：5 个 epoch、batch size 8、seed 5、学习率 `1e-4`，跑在 MPS 上，ResNet-18 接一层 256 单元的隐藏层。验证集按场景分组切分，比例 0.25。

切出来 2054 个训练窗口、673 个验证窗口。结果：

- 验证集动作准确率 **83.95%**；
- 多数类基线是 **26.75%**（全押 `dome1_fire`）；
- Pickup 召回 **80%**（48/60），Drop 召回 **100%**（18/18）。

看着还行？但接下来的数字才是重点：

- 向上移动（`ui_up`）的召回率只有 **21.74%**（5/23）；
- `ui_select` 的 5 个标签，**一个都没预测对**。

原因其实不难猜：`dome1_fire` 在数据里出现得太多，模型学会了「不知道就开火」这个偷懒但高分的策略；而 `ui_up` 和 `ui_select` 这种稀少又关键的动作，它还没学会。

我不想粉饰这些数字。它们描述的是**单个动作标签的准确率，不是游戏里能过几关**。准确率高，不代表它真的会玩。

## 这只是起点

必须说清楚：Lower v0 是一个**离线策略，不是经过验证的游戏控制器**。

它现在还不能真正操作游戏——实时推理怎么接、怎么通过操作系统级输入把动作送进游戏、以及最关键的「Upper Agent 到底该怎么给 Lower 下指令」这个边界，都还没有定。ADR-0005 只是选定了**第一个**可测量的训练契约，用来丈量「上层该管多粗、下层该管多细」这条线，而不是最终架构。

接下来要做的，是把它接到游戏里跑起来，用保留的测试场景测真正的前进/拾取/攻击成功率，再回头看这个分层边界划得对不对。如果它连一局都打不下来，那说明问题不在模型，而在我们把任务切错了地方。
